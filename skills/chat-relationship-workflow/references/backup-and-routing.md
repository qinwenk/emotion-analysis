# 备份引导与来源分流

## 用户还没有材料

先复用已知的手机系统、电脑系统、目标对象和想解决的问题。只缺路径就只问路径，不重发背景问卷。备份引导可直接说：

“先把你们的聊天保存在电脑上。电脑微信里找‘迁移与备份’或‘备份与恢复’，选择备份到电脑；在手机上确认这位联系人的聊天和时间范围。完成后，把备份文件夹的完整路径告诉我，我来识别下一步能用什么工具。”

具体入口名称、同网或连接要求以该版本界面提示为准。没有看到 UI 时不要给虚构的坐标或假装已经点击。用户要求代操作时才使用可用的 computer-use 能力并先读其 skill；手机端确认由用户完成。明确要求只导入某人时，不选择所有联系人。不要恢复或覆盖用户原有聊天来尝试导出。

备份是一份原始副本，不是通用明文导出。备份完成后仍可能缺密钥或解析器。先对用户给出的路径检查，不能让他无目的地反复备份。已有导出文件无需再造一份加密备份作为分析门槛。

## 只读探测

从新 skill 的实际目录运行，替换路径，不沿用历史对象或账号：

```powershell
python scripts/probe_source.py --source "D:/user-selected/source"
```

结果是候选类型。默认最多查看 1000 个文件、2000 个目录；扫描不完整、读取失败或跳过链接时会明确报告。按需要缩小目标目录或调整上限；不把部分扫描说成完整盘点。探测不会输出消息内容，不能证明身份映射、解密成功或聊天完整。

| 材料 | 识别与处理 |
| --- | --- |
| 微信官方 RMFH 备份 | `RMFH` 头、`RMFT` 尾，常见 ChatPackage/Index/Media。需要对应备份的 AES-GCM 数据密钥，走 RMFH 分支。 |
| Windows 微信桌面数据 | 目标账号的 db_storage，数据库及可能的 WAL/SHM。走版本匹配的桌面分支；扩展名 .db 本身不证明 SQLCipher。 |
| Apple 设备备份 | Finder/iTunes 的 Manifest 等结构，区别于微信自己的备份。要匹配设备备份工具及版本；本包没有通用设备备份导出器。 |
| ChatLab JSON/JSONL 或其他明文导出 | 跳过解密，先验证结构，再选择导入器；不支持的格式不能当作纯文本摘要导入。 |
| 已导入 ChatLab | 复用会话 ID，用只读查询核实目标与范围后直接分析。 |
| 未知格式/多个账户混杂 | 报告能确认的特征，只问区分来源的最小问题；不按文件名推断消息方向。 |

## 改用另一来源

若 RMFH 缺密钥但同一账号的桌面端已有聊天，可以提出桌面数据路线。用户只授权特定文件夹时，不扩展到其他账户或所有本机文件；用户已授权本人同一会话的完整获取时，可在其范围内继续，并明确说“接下来读取电脑端已同步的记录”。

桌面历史可能少于手机；不能把另一来源成功描述为原备份解密成功。记录实际来源、最近同步情况、覆盖时间及缺失媒体。记录里没出现的线下互动保持未知。
